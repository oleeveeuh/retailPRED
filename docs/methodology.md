# Methodology

Deep-dive companion to the README: features, models, training configuration, and exactly how the published numbers are (and are not) produced. Evidence-first — every claim here points at code or a tracked artifact.

## 1. Data pipeline

```
Census MRTS API ──► project_root/etl/fetch_mrts.py
FRED / Yahoo     ──► project_root/etl/fetch_fred.py / fetch_yahoo.py
                          │
                          ▼
        project_root/etl/build_dataset.py        (merge + clean)
                          │
                          ▼
        project_root/etl/build_multi_resolution_dataset.py
                          │
                          ▼
        project_root/data_multi_resolution/retail_<category>_multi_resolution.csv
        (~457 monthly rows stacked with weekly/daily expansions, 76 columns)
```

The multi-resolution CSVs are the training input for every model (`train.py`, `backend/ml/train_73_features.py`). They are tracked in the repository so training is reproducible without network access.

## 2. Feature set (73 features)

Built in `build_multi_resolution_dataset.py`; consumed in this exact order by training after dropping `['y', 'index', 'year']` (`backend/ml/train_73_features.py:68`):

| Family | Count | Examples |
|---|---|---|
| Temporal | 8 | `month`, `quarter`, `day_of_week`, `week_of_year`, `is_weekend`, `day_of_month`, `day_of_year` |
| Cyclical encodings | 6 | `month_sin/cos`, `quarter_sin/cos`, `day_of_year_sin/cos`, `day_of_week_sin/cos` |
| Lags (shifted — causal) | 16 | `lag_1` … `lag_52`, weekly/monthly variants |
| Rolling statistics | 30 | `rolling_mean/std_{3,6,12}` and weekly variants |
| Rate of change | 10 | `pct_change_1/12`, `diff_1/12`, `yoy_change` |
| Momentum | 2 | `momentum_30d`, `momentum_90d` (divided by *shifted* value — causal) |
| Year-over-year | 1 | `yoy_change` |

### The leakage caveat, precisely

- **Excluded correctly:** the raw `year` column is in the CSVs but explicitly dropped by every current training script. Early models exploited it ("2024 ⇒ this sales range"); that shortcut is closed.
- **Still inclusive:** `rolling_mean_*`, `rolling_std_*`, `pct_change_*`, `diff_*`, and `yoy_change` are computed with pandas defaults, i.e. **the window includes the current row's target value** (`build_multi_resolution_dataset.py:159-199`). Only `lag_*` and `momentum_*` are strictly causal.
- **Consequence:** holdout-style metrics computed on those CSVs (e.g. `training_outputs/training_report.md`, LGBM MAPE 1.42%) are optimistic and should not be quoted as expected performance.
- **Why the published table is different:** the README results come from the `prediction_log` workflow — predictions generated by the trained models for 2025 dates, stored in SQLite, and later compared to Census actuals published *after* the predictions were made. That comparison cannot be inflated by training-time feature leakage (though it has its own caveat, §5).
- The **inference-time** feature path (`backend/ml/feature_computer.py`) filters history to `date < prediction_date` before computing rolling stats, so live predictions are computed causally.

## 3. Models

### In the repository

| Model | Source | Artifacts | Notes |
|---|---|---|---|
| LightGBM | `backend/ml/train_73_features.py` (`LGBMRegressor`, 200 trees, depth 10, lr 0.05) | `backend/ml/models/{category}_LGBM_model.pkl` (~0.5 MB each) | Default serving model; dict payload `{model, features, metrics}` |
| RandomForest | same script (`RandomForestRegressor`, 200 trees, depth 15) | `backend/ml/models/{category}_RandomForest_model.pkl` (~36 MB each) | Grown without aggressive pruning → large files |
| SeasonalNaive, AutoARIMA, AutoETS | `backend/ml/train_statistical_models.py` via Nixtla `statsforecast` (`season_length=52`) | not committed | baselines / experiments |

Discovery order for serving (`backend/ml/unified_inference.py`, `backend/ml/multi_resolution_inference.py`): flat `backend/ml/models/{category}_{ModelType}_model.pkl` first, then the legacy `training_outputs/models/{Display_Name}/{ModelType}_model.pkl` layout.

### Not in the repository

- **PatchTST / TimesNet** — genuinely implemented (Nixtla `neuralforecast`) in an earlier training script (`project_root/models/robust_timecopilot_trainer.py`) that has been **removed** from the repo. Its training report survives as `training_outputs/training_report.md` (PatchTST MAPE 22.2%, TimesNet 22.5% — worse than the tree models). No neural weights are shipped; the `PatchTST`/`TimesNet` rows in `prediction_log` were produced by a trend+seasonal heuristic (`generate_rolling_predictions.py:352-413`), and their validation MAPEs measure that heuristic, not transformers.
- **AutoETS** — removed after failing badly on 2025 actuals (39–420% MAPE across configurations) during the distribution shift; see the superseded README history in git.

## 4. Training configuration

- Split: chronological, last 52 rows of each category CSV held out (`train.py:177-210`); training excludes `y`, `index`, `year`.
- Early stopping for LightGBM against the holdout.
- Per-category best-model selection by validation MAE (`train.py`), LGBM default at serving time.
- Data volume: ~457 monthly rows per category (2015→2025) plus multi-resolution expansions; small-data regime, hence the emphasis on feature engineering over architecture.

## 5. Validation methodology and its limits

`weekly_validation.py` (Airflow-scheduled, or manual: `python weekly_validation.py --date YYYY-MM-DD`):

1. Fetch actual MRTS values from the Census API for the target month.
2. Scale them into forecast units via per-category factors (`config.py:CENSUS_SCALING_FACTORS`, e.g. `total_retail_sales: 71.64`) — Census publishes in millions of dollars, forecasts are in scaled units.
3. Write the same monthly actual onto **every weekly prediction in that month** (`prediction_log.actual_value`).
4. Recompute `error_percentage` per row and export aggregates.

Consequences:

- `avg_mape` in `training_outputs/validation_metrics.json` = mean `error_percentage` over validated rows. For LGBM: 11 categories × 39 validated weeks = 429 rows, but these derive from only ~10 monthly observations per category — **the samples are pseudo-replicated**, so treat sample counts as row counts, not independent tests.
- Scaling factors were estimated by comparing training data to Census units; factor error shows up directly in MAPE (the nonstore category factor is marked "Estimated" in config).
- The authoritative table in the README is regenerated by the deleted one-off predecessor of `backend/calculate_validation_metrics.py`; recompute from `prediction_log` directly:

  ```sql
  SELECT model_name, COUNT(*), AVG(error_percentage)
  FROM prediction_log
  WHERE actual_value IS NOT NULL
  GROUP BY model_name;
  ```

## 6. Economic context & scenario analysis

- The serving API exposes economic-context indicators (CPI, unemployment, sentiment, etc., stored in `time_series_data`) and what-if scenario multipliers (recession ×0.92, recovery ×1.06, …) applied to base predictions — see `backend/services/scenario_analysis.py`.
- **Economic indicators are context/display features at serving time, not model inputs** — the trained models use only the 73 sales-history features. Marketing them as drivers would be inaccurate.

## 7. Reproducing the numbers

```bash
pip install -r requirements.txt
python backend/ml/train_73_features.py        # re-train LGBM + RF (minutes)
python validate_predictions.py --export       # rebuild data/validation_metrics.json from the DB
pytest                                        # schema, config, metric-reconciliation tests
```

The tracked `training_outputs/validation_metrics.json` (2026-02-14) is the frozen snapshot behind the README table.
